## Checklist

- **Active phase acceptance criteria and scope:** Met.
  - Domain YAML config: Pydantic `Domain`, strict, `extra=forbid`, path-safe ID.
  - Pydantic extraction schema: `ExtractionResult`. The job writer creates
    `TASK.md`, `input.jsonl` and `schema.json`, with `schema.json` generated from
    the model.
  - Result importer with schema validation and cross-reference checks against the
    trusted SQLite snapshot, not the job files. No model API is called.
  - Part A shows that an agent can read one job and produce a valid result.
  - The importer rejects uncited, out-of-range, foreign-source, unknown-kind,
    unknown-type, unreferenced-entity and `verified` claims.
  - "Unsupported" is enforced structurally (citation exists and lies in the
    job's input). Whether a statement is semantically entailed by the cited text
    is not checked, which is inherent without a model and is left for P5
    evidence work.
  - No P5+ scope creep: no consolidation, alias merging, graph or packs. The
    `extraction_results` table is P4 storage only.
- **Correctness, errors, retries and deterministic behavior:**
  - Partitioning and IDs: each video is split separately at segment boundaries by a
    character budget, and an oversize single segment gets its own part.
    `read_snapshot` already guarantees non-empty, start-ordered, finite segments, so
    `segments[0]['start']` is the minimum and an empty-lines job cannot occur. IDs
    are `<video>-<part>-sha256(schema_version, domain settings, input)[:12]`, using
    sorted-key JSON. I confirmed they are identical across processes with
    `PYTHONHASHSEED` 1, 2 and 999.
  - File writes are atomic (temp file, fsync, replace) and never touch
    `result.json`. Import is all-or-nothing per result and upserts in its own
    transaction. Byte-identical results short-circuit to `unchanged`.
  - A rejected replacement does not write SQLite, so an earlier accepted row
    survives. I reproduced this with schema-valid but cross-ref-invalid
    replacements as well as malformed JSON.
  - CLI exit codes: `rejected` gives 1, other statuses give 0, a bad
    config/domain file gives 1 with no traceback, and a missing subcommand gives 2.
  - Migration v3 is append-only (v1 and v2 unchanged) and transactional.
- **Automated tests and evidence accuracy:**
  - I independently ran **155 tests** (145 prior + 10 P4), all passing with 0
    skipped. The P4 tests cover every planned test category.
  - I verified these test-report claims: test counts, 20-file installed parity,
    dependency versions and the coverage bullets (each traced to test code).
  - Two claims could not be re-observed because they are historical and not
    persisted: the first-run regex failure and the ad-hoc rejection-reason script.
- **Provenance, untrusted input, paths and secrets:**
  - `TASK.md` contains only trusted domain YAML values, validated IDs and numbers.
    Transcript text appears only as JSON strings in `input.jsonl`.
  - Every input line keeps the source ID, the canonical URL, `source_index` and
    the start/end timestamps.
  - Stored payloads keep the job ID, domain settings, source ID, input hash, result
    hash and the normalized result. `verification_status` is
    `Literal['unverified']`, and duplicate JSON keys cannot smuggle in `verified`
    (last-wins normalization was reproduced in both key orders).
  - Editing `input.jsonl` does not widen the allowed citations, and `create`
    restores it.
  - These are rejected or reported `stale`: a `job_id` from another job or domain,
    a symlinked job folder, a symlinked, FIFO or directory `result.json`,
    oversized results, deep nesting, and non-finite or huge numbers.
  - No secrets, raw transcript collection or user data were added. All fixtures
    are synthetic.
  - New core dependencies: pydantic and PyYAML are local, open-source
    libraries with no network, hosted service, MCP or proprietary API. Pydantic
    is named by the plan, and the standard library has no YAML parser. This is
    consistent with the project invariants.

  - P4 is `in_progress` with tests and review pending, and

## Findings

**No blocking issues found.** All findings below are non-blocking.

- **N1 — Import command is cwd-dependent and silently a no-op elsewhere**
  - Location: `src/kforge/builder/jobs.py:194` (TASK.md text) and `:272-273`.
  - Impact: `TASK.md` tells the agent to run `kforge jobs import <domain.yaml>`
    but not from where. Paths resolve from the working directory or environment.
    I ran it from inside a copy of the job folder, and it printed `[]` with exit 0,
    which looks the same as "nothing to import". An agent could wrongly believe its
    result was imported.
  - Fix: have `TASK.md` say to run the command from the directory or config used
    for `kforge jobs create`. Or have `import` warn or exit nonzero when the
    domain's jobs folder does not exist.
  - Verify: rerun import from inside a job folder and expect a clear message or a
    nonzero exit.
- **N2 — Span+overlap citation check accepts a zero-length boundary touch**
  - Location: `src/kforge/builder/jobs.py:255-259`.
  - Impact: a citation [0.9, 0.95] is accepted when one segment ends at 0.9 and the
    next starts at 1.0, although it covers almost only the gap. A citation fully
    inside the gap ([0.95, 0.99]) is correctly rejected. The test report
    discloses this limitation.
  - Fix: require positive overlap (`line['start'] < citation.end and
    citation.start < line['end']`, keeping zero-length segments in mind) or
    exact segment-boundary matching. At minimum, P5 must map citations back to
    segments before treating a span as evidence.
  - Verify: add the boundary-touch case to `test_missing_foreign_and_invalid_citations_are_rejected`.
- **N3 — Stored results can outlive the transcript they cite**
  - Location: `jobs.py:303-306` together with
    `src/kforge/ingest/transcripts.py:98`.
  - Impact: `TranscriptStore.save` replaces the canonical record on re-ingest
    (upsert). An accepted result keeps its job ID and `input_sha256`, but not the
    cited segment text or `source_index`. After re-ingest with different
    captions, its timestamps may point at different text. Import then reports the
    folder `stale`, but the SQLite row remains. This is detectable (the job ID is
    absent from the current plan, or the input hash differs), so provenance is not
    silently corrupted. The test report only mentions the domain-settings case.
  - Fix: record in HANDOFF/DECISIONS that P5 must consolidate only rows whose
    `job_id` is in the current plan (or whose `input_sha256` matches). Optionally
    store the cited segment snapshot.
  - Verify: a P5 test that re-ingests changed captions and asserts old rows are
    excluded or flagged.
- **N4 — Job ID docstring overclaims, and `unchanged` never revalidates**
  - Location: `jobs.py:122-126` and `:296-298`.
  - Impact: the docstring says IDs hash "everything an agent sees". In fact the
    `TASK.md` template, `schema.json` content and the importer's validation rules
    are not hashed; only `RESULT_SCHEMA_VERSION` is. If rules or wording change in
    code without a version bump, existing results keep the same job IDs and
    short-circuit to `unchanged` without revalidation.
  - Fix: correct the docstring, and bump `RESULT_SCHEMA_VERSION` (or add a job
    format version to the digest) whenever instructions or validation change.
    Note this in DECISIONS.
  - Verify: a unit test that changing the version changes job IDs.
- **N5 — Error locations echo agent-supplied keys**
  - Location: `jobs.py:87-90`.
  - Impact: the comment says submitted values are never echoed, but Pydantic
    `loc` includes unknown object keys verbatim and with unbounded length. A
    50-character extra key was printed as the error location. Impact is low: the
    output is JSON-encoded and the text is the agent's own output.
  - Fix: replace or truncate `loc` parts for `extra_forbidden` errors.
  - Verify: an extra-key subtest asserting a bounded or generic location.
- **N6 — Upgrade friction for existing v2 stores**
  - Location: `storage.py:21-25` together with the existing
    `export/transcripts.py:101-102`.
  - Impact: after installing P4, `kforge export` and `kforge jobs create` on a
    P3 (v2) store exit 1 with "Database schema must be initialized at the current
    version" until `kforge init` (or a scrape) is run. I reproduced this; after
    `init`, export succeeded. It is documented in README and the test report, but
    the message does not name the remedy.
  - Fix: add "run `kforge init`" to the message, or record it in HANDOFF.
  - Verify: the reproduction step 11 below.
- **N7 — Status semantics**
  - Location: `jobs.py:286-288` and `cli.py:99`.
  - Impact: deleting an already-imported `result.json` reports `pending` while
    SQLite still holds the accepted row. `stale` folders exit 0.
  - Fix: document both, or report the stored state.
  - Verify: the reproduction step 8b below.
- **N8 — Knowledge and evidence precision**
  - Location: `docs/project-knowledge/DECISIONS.md:5-6` and
    `docs/test-reports/P4.md` item 5.
  - Impact: the P0 decision "no runtime dependency" is superseded by the P4 core
    dependencies and needs a P4 decision entry (part of the pending knowledge
    gate). Separately, test-report item 5 records `git diff --check`; once all
    changes are staged, that compares an identical worktree and index and checks
    nothing. My `git diff --cached --check` passed, so there is no defect, only
    imprecise evidence.
  - Fix: add the decision entry, and record the `--cached` variant.
